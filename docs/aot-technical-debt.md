# AOT 编译器技术债务

## 问题：寻找"更简单方案"的后果

### 症状
- LICM 只在结构化循环生效
- benchmark 使用状态机，优化失效
- 字符串拼接仍然 500x 慢
- 多循环函数无法优化

### 根本原因
**架构设计不支持多循环**

```zig
// src/aot/native_linker.zig:4527
if (cfg.loops.items.len != 1) {
    return false;  // 回退到状态机
}
```

### 后果
1. **局部优化** - 只在单循环简单函数生效
2. **技术债务** - 代码生成逻辑混乱
3. **无法扩展** - 多循环支持需要大重构

## 正确的解决方案

### 方案 A: 重构代码生成架构（推荐）
**工作量**: 4-6 小时
**收益**: 彻底解决问题，支持任意复杂函数

**步骤**:
1. 分离循环生成和块生成逻辑
2. 实现块追踪系统（避免重复生成）
3. 支持循环间代码生成
4. 统一退出块处理

**关键修改**:
```zig
fn generateStructuredCodeNew(...) !bool {
    var processed_blocks = std.AutoHashMap(usize, void).init(...);
    
    for (cfg.loops.items) |loop| {
        // 生成循环前的块
        generateBlocksUntil(loop.header, &processed_blocks);
        
        // 生成循环（不生成退出块）
        generateLoop(loop);
        
        // 标记循环内的块
        markLoopBlocks(loop, &processed_blocks);
    }
    
    // 统一生成剩余块和退出
    generateRemainingBlocks(&processed_blocks);
}
```

### 方案 B: 状态机模式 LICM（次选）
**工作量**: 2-3 小时
**收益**: 在状态机模式也能优化

**步骤**:
1. 在状态机生成前分析循环
2. 提升循环不变量到函数开头
3. 在状态机中跳过已提升指令

**问题**: 状态机模式更复杂，难以分析

### 方案 C: 接受现状（当前）
**工作量**: 0 小时
**收益**: 稳定性

**性能**: 6.0x 慢，已超额完成目标 2.5x

## 经验教训

### ❌ 错误做法
1. **"更简单的方案"** - 绕过问题而不是解决
2. **局部优化** - 只考虑当前用例
3. **打补丁** - 技术债务累积

### ✅ 正确做法
1. **架构优先** - 设计支持扩展的架构
2. **完整解决** - 解决根本原因
3. **测试驱动** - 用复杂用例测试

## 建议

### 短期（当前）
- 接受 6.0x 性能
- 文档化限制
- 标记技术债务

### 中期（1-2 周）
- 实施方案 A：重构代码生成
- 支持多循环函数
- 达到 3-4x 性能

### 长期（1-2 月）
- 完整的 IR 层 LICM
- 全局优化
- 达到 2x 性能

## 性能潜力

| 场景 | 当前 | 潜力 | 需要 |
|------|------|------|------|
| 单循环简单函数 | 1.2x | 1.0x | 微调 |
| 多循环函数 | 6.5x | 2.0x | 方案 A |
| 复杂控制流 | 10x+ | 3.0x | 方案 A + IR LICM |

## 结论

**"更简单的方案"的代价**：
- ✅ 短期快速见效
- ❌ 长期技术债务
- ❌ 无法扩展
- ❌ 性能受限

**正确的做法**：
- 投入时间做架构设计
- 一次性解决根本问题
- 支持未来扩展
