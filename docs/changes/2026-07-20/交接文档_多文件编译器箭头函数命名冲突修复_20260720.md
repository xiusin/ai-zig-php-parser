## 一、TL;DR（高层摘要）

本次会话修复了多文件 AOT 编译器 `mergeModules` 中两个连环 P0 缺陷：

1. **Use-after-free**：`rename_map.put(new_func.name, renamed)` 存入旧名指针后立即 `free(new_func.name)`，导致哈希表键悬空，后续查找全部返回乱码/失败。
2. **const_string 未更新**：箭头函数/闭包名通过 `const_string` 指令存入字符串表传递给 `php_create_closure` 作为回调名，重命名后仅更新 `call.func_name` 而未更新 `const_string`，导致运行时回调找不到函数。

修复后 `blog_system`（7 文件）和 `ecommerce`（6 文件）多文件项目从运行时崩溃 → 完整通过。单文件无回归。

### 4.2 缺陷一：Use-after-free

#### 问题代码

```zig
// src/aot/multi_file_compiler.zig  mergeModules()  修复前
const renamed = std.fmt.allocPrint(self.allocator, "{s}_mf{d}", .{ new_func.name, file_idx }) catch new_func.name;
try rename_map.put(new_func.name, renamed);  // 键 = new_func.name 指针
if (new_func.name_owned) {
    self.allocator.free(new_func.name);       // ← 释放了键指向的内存！键悬空！
}
new_func.name = renamed;
```

后续 `rename_map.get(call_op.func_name)` 查找时，键比较访问已释放内存，返回乱码或失败。

#### 修复代码

```zig
// 修复后
const renamed = std.fmt.allocPrint(self.allocator, "{s}_mf{d}", .{ new_func.name, file_idx }) catch new_func.name;
// 复制旧名作为 rename_map 的键，因为下方会释放原 new_func.name
const old_name_copy = try self.allocator.dupe(u8, new_func.name);
try rename_map.put(old_name_copy, renamed);  // 键 = 独立副本
if (new_func.name_owned) {
    self.allocator.free(new_func.name);       // 安全：键是独立副本
}
new_func.name = renamed;
```

#### defer 清理

```zig
var rename_map = std.StringHashMap([]const u8).init(self.allocator);
defer {
    var rit_clean = rename_map.iterator();
    while (rit_clean.next()) |rn_entry| {
        self.allocator.free(rn_entry.key_ptr.*);  // 释放键副本
    }
    rename_map.deinit();
}
```

### 4.3 缺陷二：const_string 未更新

#### 问题分析

箭头函数/闭包的名字在 IR 中有**两条使用路径**：

1. `Function.name` 字段 → 被 `call` 指令的 `func_name` 引用 → 重命名时**已更新** ✅
2. `const_string` 指令 → 存入字符串表 → 传递给 `php_create_closure` 作为回调名 → **未更新** ❌

修复前仅更新路径 1，路径 2 中 `php_create_closure` 收到旧函数名 `__arrow_3`，而实际函数已更名 `__arrow_3_mf1`，运行时找不到函数。

> **IR 生成代码**（`ir_generator.zig` 第 8726-8745 行）证实了这一路径：
> ```zig
> // Closure name
> const name_id = try self.module.?.internString(name_copy);
> const name_reg = try self.emitWithResult(.{ .const_string = name_id }, .php_string);
> // Call php_create_closure
> return self.emitWithResult(.{ .call = .{
>     .func_name = "php_create_closure",
>     .args = args,  // args[0] = name_reg (const_string)
>     ...
> } }, .php_callable);
> ```

#### 修复代码

```zig
// 记录此文件函数在 merged.functions 中的起始索引
const func_start_idx = merged.functions.items.len;

// ... 函数合并循环 ...

// 回溯更新 const_string 中的箭头函数/闭包名引用
if (rename_map.count() > 0) {
    for (merged.functions.items[func_start_idx..]) |func| {
        for (func.blocks.items) |block| {
            for (block.*.instructions.items) |*inst| {
                if (inst.*.op == .const_string) {
                    const str_idx = inst.*.op.const_string;
                    if (str_idx < merged.string_table.items.len) {
                        const str_val = merged.string_table.items[str_idx];
                        if (rename_map.get(str_val)) |new_name| {
                            const new_name_id = try merged.internString(new_name);
                            inst.*.op = .{ .const_string = new_name_id };
                        }
                    }
                }
            }
        }
    }
}
```

### 5.3 根因链条

```
多文件编译 → 箭头函数名冲突（__arrow_N 重复）
  → rename_map.put(旧名, 新名)  ← 旧名是指针
    → free(旧名)  ← 指针悬空！
      → rename_map.get() 返回乱码  ← call 指令重命名失效
        → const_string 也未被更新  ← php_create_closure 收到旧名
          → 运行时回调找不到函数 → 返回 null → "Call to member function on non-object"
```

## 六、已知问题（未修复）

### 6.1 P1: web_framework 16 文件多文件编译 OOM

- **现象**: `Error: Multi-file compilation failed: OutOfMemory`
- **根因**: `mergeModules` 全量拷贝所有文件的 IR 函数/字符串表/类型定义到 merged module，16 文件时内存峰值过高
- **影响**: `web_framework` 项目无法 AOT 编译
- **建议方向**: 流式合并（逐文件处理并释放源 IR）或分阶段合并

### 6.2 P2: Markdown 渲染不完整

- **现象**: AOT 的 `MarkdownRenderer` 输出 `<p># Introduction</p>` 而非 `<h1>Introduction</h1>`
- **影响**: `blog_system` 输出与 PHP 存在差异（已知差异，非 AOT 缺陷）
- **建议方向**: 完善 `MarkdownRenderer` 支持标题/列表/代码块等基础语法

### 6.3 P2: test-aot 编译错误

- **现象**: `zig build test-aot` 报 6 个编译错误
- **根因**: `linker.zig:162` 使用 `.references = .{}` 但 Zig 0.16.0 的 `ArrayList` 需要 `items` 和 `capacity` 字段；`dependency_resolver.zig:140` 的 `init` 函数签名不匹配
- **影响**: AOT 模块自动化测试无法运行
- **注意**: 此为预存问题，与本次修复无关

### 6.4 PHP 脚本自身 bug（非 AOT 问题）

`blog_system` 和 `ecommerce` 的 `Database.php` 中 `update` 方法使用 `$this->tables[$table] ?? []`，`??` 运算符返回值副本（非引用），导致 `foreach (&$row)` 不写穿原始数组。AOT 行为反而**更正确**（直接修改原数组）。

### 6.5 单文件通过率偏低

- **当前**: 85/180 = 47.2%
- **主要失败原因**: `fuzzy_scripts_720` 中大量脚本本身在 PHP 解释器下就报错（exit=255），被标记为 SKIP
- **编译失败**: 18 个（如 `f029`、`f030` 报 "Zig compiler failed with exit code 1"）
