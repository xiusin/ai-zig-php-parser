## 二、已完成任务

### 2.1 P1：cond_br 中 php_lt/le/gt/ge i64 快速路径优化

#### 根因分析

循环 header 块的 `cond_br` 条件检查通过 `writeInlinedConditionExpr` 独立生成（`native_linker.zig` line ~15616 的 `if (!(` + line ~15631 `writeInlinedConditionExpr`），而非走 `generateInstructionSimple` 的 `.lt` 分支。

此前 `writeInlinedConditionExpr` 的 `else` 分支直接生成 `(try runtime.php_lt(reg, reg)).toBool()`，**无 i64 快速路径**，导致循环条件检查每次迭代都调用重量级运行时函数。

#### 修复内容

| 文件 | 函数 | 行号（约） | 变更点 |
|------|------|-----------|--------|
| `src/aot/native_linker.zig` | `writeInlinedConditionExpr` | ~16000-16106 | `.lt`/`.le`/`.gt`/`.ge` 四分支的 `else` 分支添加 `i64_loop_optimize_active` 检查，生成 `if (reg.isInt() and reg.isInt()) asInt() OP asInt() else php_X()` 快速路径 |
| `src/aot/native_linker.zig` | `generateInstructionSimple` | ~9267-9516 | 四分支类型条件从 `php_value and php_value` 扩展为 `(php_value or i64) and (php_value or i64)` |
| `src/aot/native_linker.zig` | `generateInstructionSimple` | ~9340/9399/9458 | `.le`/`.gt`/`.ge` 三分支新增 i64 快速路径（此前仅 `.lt` 有） |

#### 关键技术细节

1. **类型条件扩展原因**：`const_int 5` 的 IR 类型是 `i64`，而 `global_get $i` 的类型是 `php_value`。`$i < 5` 的操作数类型为 `php_value and i64` 混合，此前不命中 `php_value and php_value` 条件，导致 i64 快速路径不激活。

2. **alloca 指针安全**：
   - `writeInlinedConditionExpr` 中使用 `resolveLoadSource` + `alloca_regs` 检查生成 `.*` 后缀
   - `generateInstructionSimple` 中保持与原 `.lt` 分支一致的无后缀风格

3. **生成代码对比**（以 `simple_loop.php` 为例）：

   变更前：
   ```zig
   if (!((try runtime.php_lt(reg_1, reg_2)).toBool())) { @branchHint(.unlikely); break; }
   ```

   变更后：
   ```zig
   if (!((if (reg_1.isInt() and reg_2.isInt()) (reg_1.asInt() < reg_2.asInt()) else (try runtime.php_lt(reg_1, reg_2)).toBool()))) { @branchHint(.unlikely); break; }
   ```

### 2.2 P2：while 循环 i64 快速路径

#### 结论：无需额外修改，已自动激活

**发现**：while 循环因 `detectLoops` 的 increment-in-body 检测（body 块末尾有 `php_increment`），自动被识别为 for 循环并激活 `generateOptimizedForLoop`，与 for 循环走相同 `generateStandardForLoop` 路径。

**验证**（`while_loop.php` 生成代码）：
```zig
// DEBUG generateStandardForLoop header=1 body_start=2 blocks_count=2 increment=null
while (true) {
    // Header: while_cond_0
    reg_1 = getGlobalVar("$i");
    if (!((if (reg_1.isInt() and reg_2.isInt()) (reg_1.asInt() < reg_2.asInt()) else (try runtime.php_lt(reg_1, reg_2)).toBool()))) { @branchHint(.unlikely); break; }
    // ...
    reg_6 = if (reg_5.isInt()) runtime.Value.initInt(reg_5.asInt() + 1) else try runtime.php_increment(reg_5);
}
```

`php_lt` 和 `php_increment` 均已激活 i64 快速路径。

## 五、已知问题

### 5.1 `generateInstructionSimple` 中 i64 快速路径不处理 alloca 指针

**现状**：`generateInstructionSimple` 的 lt/le/gt/ge i64 快速路径直接用 `reg_{d}` 不添加 `.*` 后缀。

**风险**：若 body 块中有 alloca 指针类型的比较操作数，可能不正确。

**缓解**：与之前 `.lt` 分支的实现一致，非本次引入。`writeInlinedConditionExpr` 中已正确处理（使用 `resolveLoadSource` + `alloca_regs` 检查）。

### 5.2 运行时 `isInt()` 检查开销

**现状**：每次循环条件检查都有两次 `isInt()` 调用。

**影响**：整数循环条件跳过 `php_lt` 函数调用的收益被部分抵消。

**解决方案**：编译时类型分析（P1 后续任务）。

### 5.3 `if-else` 表达式分支预测

**现状**：Zig 的 `if-else` 表达式不支持直接加 `@branchHint`。

**影响**：编译器可能为 `if-else` 表达式生成分支预测，i64 路径更可能执行但未提示。

**缓解**：性能影响微小，暂不处理。

### 5.4 全量测试脚本超时问题

**现状**：`scripts/full_regression_test.sh` 在 3 分钟内无法完成全部测试（`fuzzy_scripts_715/fail_runtime` 目录被截断）。

**临时方案**：单独补测 `fuzzy_scripts_715/fail_runtime` 的 6 个脚本。

**建议**：优化测试脚本并行度或拆分为多个子脚本。
