## 一、本会话完成任务

### 1.1 f070 PHI 一致性修复 ✅

**问题**: `foreach` 循环体内嵌套 `if/else/if/else` 结构时，merge 块的 PHI 赋值在 `body_block_indices` 的 for 循环中被**无条件**生成，覆盖了 THEN/ELSE 分支内的正确值。

**根因分析**:
- IR 结构: `foreach_body_1` → `if_then_5`(deposited) / `if_else_6` → `if_then_8`(withdrawn) / `if_merge_9`(other) → `if_merge_7` → `foreach_increment_2`
- `if_merge_9` 的 br 到 `if_merge_7` 在 `body_block_indices` for 循环中被无条件处理
- 生成的 `reg_70 = reg_71`（`if_merge_7` 的 PHI from `if_merge_9`）覆盖了 THEN 路径（`if_then_5 → if_merge_7`）的值
- 导致循环变量（balance）在第二次迭代时丢失前一次迭代的值

**修复方案**（`src/aot/native_linker.zig`，+163 -91 行）:

| 变更点 | 位置 | 说明 |
|--------|------|------|
| 新增字段 `cond_br_merge_phi_generated` | ~line 255 | `?*std.AutoHashMap(usize, void)`，跟踪已被 cond_br 分支内处理过 PHI 的 merge 块索引集合 |
| `generateCondBrBlock` THEN merge→merge | ~line 13101 | THEN merge 点的 br-to-exit 检查后，添加 `else if` 处理 merge 块 br 到另一个 merge 块的情况，在 THEN 分支内生成目标 merge 块的 PHI 赋值 |
| `generateCondBrBlock` ELSE merge→merge | ~line 13246 | 对称处理，在 ELSE 分支内生成目标 merge 块的 PHI 赋值 |
| `generateBrChain` merge→merge 链式 | ~line 13408 | merge point handler 中添加链式处理，检查 `!processed.contains` + `countPredecessors > 1`，生成并标记目标 merge 块 |
| `body_block_indices` setup | ~line 14050 | 创建 `cond_br_merge_phi_set`，save/restore `self.cond_br_merge_phi_generated` |
| `body_block_indices` `target_phi_handled` | ~line 14405 | 当源块和目标块都在 `cond_br_merge_phi_generated` 集合中且都是 merge 块（`countPredecessors > 1`）时，跳过 `generateBrChain` 调用 |

**关键设计决策**:
- **不修改 `isMergeBlock`** — 保持原始回边检测逻辑（使用块索引 `blk_idx > block_idx` 判断回边），避免影响嵌套循环头检测
- **不修改 `go` 函数**（`generateStandardForLoop` 路径）— f070 使用 `body_block_indices` 路径（foreach 循环），不需要修改 `go` 函数
- **移除 `!processed_body.contains(br_target_idx)` 检查** — 因为 `br_target_idx != header_idx` 已经排除了循环头，merge 块即使已在 `processed_body` 中也可以安全跳过
- **在 `generateCondBrBlock` 和 `generateBrChain` 的 merge→merge 处理中保留 `!processed.contains` 检查** — 防止为循环头（在 `processed` 中）生成错误的 PHI

### 3.1 f090 Promise.all 闭包变量捕获缺陷

**现象**: AOT 编译 `f090_promise_future_async_concurrent.php` 时，闭包内捕获的外层变量值不正确，导致 Promise.all 的并发执行结果与 PHP 解释器不一致。

### 3.2 `go` 函数 merge→merge 链式处理

**背景**: 本次修复只修改了 `body_block_indices` 路径（while/foreach 循环），未修改 `go` 函数（`generateStandardForLoop`，for 循环路径）。

**原因**: f070 使用 foreach 循环，走 `body_block_indices` 路径。for 循环走 `generateStandardForLoop` → `go` 函数。如果 for 循环中出现类似的 merge→merge 模式（嵌套 if/else 的 merge 块 br 到外层 merge 块），可能需要类似的修复。

**风险评估**: 低。for 循环的 IR 结构通常比 foreach 简单（循环变量在 increment 块更新，不需要复杂的 PHI 处理）。但作为预防性修复，建议添加。

## 四、已知问题

### 4.1 f004 测试脚本路径问题

**现象**: `f004_oop_deep_inheritance_magic.php` 在回归测试中显示 RUNFAIL，但手动运行可以通过。

**原因**: 测试脚本中 `aot_compile_*` 二进制文件的输出路径与测试脚本的运行路径不匹配。

**影响**: 非真实失败，不影响 AOT 编译器功能。

### 4.2 f090 Promise.all 闭包缺陷

见待办 3.1。

### 4.3 `cond_br_merge_phi_generated` 是全局状态

**现象**: `cond_br_merge_phi_generated` 是 `Self` 结构体的字段，通过 save/restore 机制保证嵌套循环正确性。

**潜在风险**: 如果在递归调用中忘记 save/restore，可能导致状态泄漏。

**缓解措施**: 当前在 `body_block_indices` 入口处使用 `defer` 保证 restore。如果后续在其他路径使用，需要同样处理。

### 4.4 `generateBrChain` 回边处理器标记循环头

**现象**: `generateBrChain` 的 merge point handler 会标记回边目标（包括循环头）到 `cond_br_merge_phi_generated` 集合中。

**为什么不是问题**: `body_block_indices` 的 `target_phi_handled` 检查通过 `br_target_idx != header_idx` 已排除循环头，不会错误跳过循环变量更新。

### 5.1 `go` 函数 merge→merge 链式处理方案

如果需要在 `go` 函数中添加类似修复：

1. 在 `generateStandardForLoop` 调用 `go` 之前，设置 `cond_br_merge_phi_generated`
2. 在 `go` 的 br handler 中（visited block handler 和 merge block handler），在 `depth == 2`（顶层）时检查 `cond_br_merge_phi_generated` 并跳过
3. 在 `go` 的 merge block handler 中添加 merge→merge 链式处理（使用 `countPredecessors > 1` + `!visited.contains`）
4. 在 `go` 的 cond_br handler 的 `else_is_merge` 路径中添加 merge→merge 链式处理

**注意**: 之前尝试过修改 `go` 函数，但导致了 f027/f176 回归。根因是 `go` 函数的 `else_is_merge` 路径中 merge 块在 if 之后被处理（`go` 递归调用），其 br 到 `if_merge_7` 通过 visited block handler 生成 PHI。如果添加 `cond_br_merge_phi_generated` 检查跳过，会跳过 ELSE 路径需要的 PHI 生成。需要更精细的条件判断（可能需要区分 THEN/ELSE 路径的 `cond_br_merge_phi_generated` 标记）。

### 5.2 `cond_br_merge_phi_generated` 改为 per-cond_br 作用域

当前 `cond_br_merge_phi_generated` 是一个全局集合，在 `body_block_indices` 入口处创建，所有 `generateCondBrBlock` 和 `generateBrChain` 调用共享。

可以考虑改为每次 `generateCondBrBlock` 调用时创建新的集合，只跟踪当前 cond_br 的 THEN/ELSE 分支内处理的 merge 块。这样可以避免跨 cond_br 的误标记。

但需要注意：`body_block_indices` 的 `target_phi_handled` 检查需要访问所有 cond_br 的标记，所以需要将多个集合合并或使用层级查找。

### 6.1 f070 IR 结构

```
foreach_cond_0:
  cond_br reg_16, foreach_body_1, foreach_cleanup_3
foreach_body_1:
  cond_br reg_23, if_then_5, if_else_6      ← 外层 if/else
if_then_5:                                     ← deposited 路径
  br if_merge_7
if_else_6:                                     ← not-deposited 路径
  cond_br reg_35, if_then_8, if_merge_9      ← 内层 if/else
if_then_8:                                     ← withdrawn 路径
  br if_merge_9
if_merge_9:                                     ← 内层 merge（2 前驱: if_then_8, if_else_6）
  br if_merge_7
if_merge_7:                                     ← 外层 merge（2 前驱: if_then_5, if_merge_9）
  br foreach_increment_2
foreach_increment_2:
  br foreach_cond_0                            ← 回边
```
