## 一、TL;DR（高层摘要）

本次会话在前一轮（2026-07-20 多文件编译器箭头函数命名冲突修复）基础上，继续修复 AOT 编译器中的指针层级和嵌套循环代码生成缺陷：

1. **嵌套循环外层 while 提前闭合**：`generateForLoopWithChildren` 中 increment 块、PHI 更新、while 闭合 `}` 均在 `for (loop.children.items)` 循环内部，当存在多个子循环时，第一个子循环处理完后即闭合了外层 while 循环，导致后续子循环和增量代码出现在 while 循环之外，产生 `expected type expression, found 'return'` 编译错误。**已修复**（f138 验证通过）。

2. **引用参数指针层级（A类）**：`store` 指令中 `ref_param_alloca`（`**Value`）、`ref_ptr`（`*Value`）、普通 `alloca`（`*Value`）三种指针类型的解引用/赋值逻辑不完整，导致 `expected type '*runtime_lib.Value', found 'runtime_lib.Value'` 编译错误。**部分修复**（12/18 编译通过，f064 仍有残留）。

3. **`writePtrAwareAssign` 缺少 ref_ptr 解引用**：`ref_ptr ← value` 和 `value ← ref_ptr` 两种赋值方向缺少解引用处理。**已修复**。

4. **`generateCondBrBlock` PHI 赋值缺少指针解引用**：合并块 PHI 赋值 `reg_{d} = {s}` 未检查目标寄存器是否是指针类型。**已修复**。

5. **`ptr_is_optimized` 判断缺陷**：`store` 指令中 `is_real_alloca` 为 true 时，`ptr_is_optimized` 仍可能为 true，导致 alloca 寄存器走错误的 mem2reg 路径。**已修复**。

编译通过率从 0/18 提升到 12/18（f064 仍有类型不匹配残留）。

## 四、核心变更详解

### 4.1 修改一：嵌套循环外层 while 提前闭合修复

**文件**: `src/aot/native_linker.zig`
**函数**: `generateForLoopWithChildren`（第 17470-17767 行）
**影响脚本**: f064, f138（`expected type expression, found 'return'`）

#### 问题

`generateForLoopWithChildren` 中，increment 块生成、PHI 节点更新、while 循环闭合 `}` 三段代码均在 `for (loop.children.items)` 循环内部。当外层循环有多个子循环时，第一个子循环处理完后即生成了 `}`，提前闭合了外层 while 循环。后续子循环和增量代码出现在 while 循环之外，Zig 编译器报 `expected type expression, found 'return'`。

#### 根因

```zig
// 修复前（简化）
for (loop.children.items) |child_idx| {
    // ... 生成子循环 ...
    // ... 生成 post-loop 块 ...
    // 生成 increment 块      ← 在 for 内部！
    // 更新所有 PHI 节点      ← 在 for 内部！
    try writer.writeAll("    }\n");  ← while 闭合在 for 内部！
}
```

#### 修复

将 increment 块、PHI 更新、while 闭合 `}` 移到 `for` 循环之外：

```zig
// 修复后（简化）
for (loop.children.items) |child_idx| {
    // ... 生成子循环 ...
    // ... 生成 post-loop 块 ...
}
// 生成 increment 块（在所有子循环之后，while 闭合之前）
if (effective_inc_idx) |inc_idx| { ... }
// 更新所有 PHI 节点（在所有子循环之后，while 闭合之前）
for (header_block.instructions.items) |inst| { ... }
try writer.writeAll("    }\n");  ← while 闭合移到 for 外部
```

### 4.2 修改二：`writePtrAwareAssign` 添加 ref_ptr 解引用

**文件**: `src/aot/native_linker.zig`
**函数**: `writePtrAwareAssign`（第 490-522 行）

#### 问题

原代码仅处理 `result_is_ref_ptr or value_is_ref_ptr` 的组合情况（指针拷贝），未区分 `ref_ptr ← value` 和 `value ← ref_ptr` 两种方向，导致类型不匹配。

#### 修复

```zig
// 修复前
} else if ((result_is_ref_ptr or value_is_ref_ptr)) {
    try writer.print("{s}reg_{d} = reg_{d};\n", .{ indent, result_id, value_id });
}

// 修复后
} else if (result_is_ref_ptr and value_is_ref_ptr) {
    // ptr ← ptr: 指针拷贝
    try writer.print("{s}reg_{d} = reg_{d};\n", .{ indent, result_id, value_id });
} else if (result_is_ref_ptr) {
    // ref_ptr ← value: 解引用赋值（ref_ptr 是 *Value，需写入 .* ）
    try writer.print("{s}reg_{d}.* = reg_{d};\n", .{ indent, result_id, value_id });
} else if (value_is_ref_ptr) {
    // value ← ref_ptr: 读取指针指向的值
    try writer.print("{s}reg_{d} = reg_{d}.*;\n", .{ indent, result_id, value_id });
}
```

### 4.3 修改三：`generateCondBrBlock` PHI 赋值添加指针解引用

**文件**: `src/aot/native_linker.zig`
**函数**: `generateCondBrBlock`（第 12912 行）
**影响脚本**: f064（`expected type '*Value', found 'Value'`）

#### 问题

合并块（多前驱）的 PHI 赋值 `reg_{d} = {s}` 未检查目标寄存器是否是 alloca/ref_ptr 指针类型，直接赋值导致类型不匹配。

#### 修复

```zig
// 修复后：添加指针解引用检查
const phi_deref = if (self.isPointerReg(phi_res.id)) ".*" else "";
try writer.print("{s}reg_{d}{s} = {s};\n", .{ child_indent, phi_res.id, phi_deref, phi_ref });
```

### 4.4 修改四：`store` 指令 `ptr_is_optimized` 判断修复

**文件**: `src/aot/native_linker.zig`
**函数**: `generateInstructionSimple` 中 `.store` 分支（第 7892 行）

#### 问题

```zig
const ptr_is_optimized = (ptr_tag == .ptr and !is_real_alloca) or ptr_tag != .ptr;
```

当 `is_real_alloca` 为 true 但 `ptr_tag != .ptr` 时，`ptr_is_optimized` 仍为 true，导致 alloca 寄存器走 mem2reg 路径（直接赋值 `reg_X = reg_Y`），而非指针解引用路径（`reg_X.* = reg_Y`）。

#### 修复

```zig
// 修复后：真正的 alloca 寄存器始终需要解引用处理
const ptr_is_optimized = !is_real_alloca and ((ptr_tag == .ptr and !is_real_alloca) or ptr_tag != .ptr);
```

## 六、已知问题（未修复）

### 6.1 f064 类型不匹配（P0，编译失败）

- **现象**: `main.zig:13101:17: error: expected type '*runtime_lib.Value', found 'runtime_lib.Value'`
- **根因**: `reg_9`（`*Value` 类型）被赋值为 `reg_4`（`Value` 类型），缺少 `.*` 解引用
- **影响**: f064 无法编译
- **建议方向**: 检查 `reg_9` 在 `current_alloca_regs` 和 `current_ref_ptr_regs` 中的状态，确认参数默认值处理代码路径

### 6.2 f071/f089 unreachable code（P0，编译失败）

- **现象**: `main.zig:9159:30: error: unreachable code`
- **根因**: 嵌套循环中 `break` 之后仍生成了代码
- **影响**: f071, f089 无法编译
- **建议方向**: 检查 `generateLoopBodyFromBlock.go` 中 `break` 生成后的 `return` 逻辑，确保 break 后不再生成后续块代码

### 6.3 f128/f149 语法错误（P0，编译失败）

- **现象**: `main.zig:11530:156: error: expected ',' after field`
- **根因**: 生成的 Zig 结构体字面量字段之间缺少逗号
- **影响**: f128, f149 无法编译
- **建议方向**: 检查匿名结构体/数组字面量的代码生成逻辑

### 6.4 f029/f030 运行时 SIGSEGV（P1，编译通过）

- **现象**: 编译通过，运行时 `exit=139`（SIGSEGV）
- **根因**: 引用参数在递归调用中传递不正确（null 值）
- **影响**: f029, f030 运行时崩溃
- **建议方向**: 检查 `writeValueArgsArrayWithRefsOffset` 对引用参数的 `initRef` 包装逻辑

### 6.5 web_framework 16 文件 OOM（P1）

- **现象**: `Error: Multi-file compilation failed: OutOfMemory`
- **根因**: `mergeModules` 全量拷贝所有文件 IR，16 文件时内存峰值过高
- **影响**: web_framework 项目无法 AOT 编译
- **建议方向**: 流式合并（逐文件处理并释放源 IR）

### 6.6 77 个运行时差异（P2）
