## 二、已完成任务

### 2.1 修复 `is_nested_loop` 误判（提交 `460d38b`）

**问题**：`generateCondBrBlock` 函数中的 `is_nested_loop` 检测仅检查 `then` 块的 `br` 目标是否已被 `processed.contains()` 标记。但 `if` 语句的 `then` 块也可能 `br` 到已处理的 merge 点（如外层 `if` 的汇聚点或循环体块），导致误判为嵌套循环。

**后果**：生成 `while(true){if(!cond)break;...}` 但缺少末尾 `break`，条件为 true 时形成无限循环。在 ReleaseFast 下表现为超时（exit=124）或段错误（exit=139）。

**修复**：增加 `current_cond_br_header_idx` 校验，只有 `br` 目标 == 当前循环头索引时才标记为嵌套循环（真正的回边），否则生成标准 `if(cond){...}` 模式。

**影响**：修复 5 个脚本（f051, f056, f085, f104, f161）。

### 2.2 修复 `generateStandardForLoop` 中 `return_generated` 未重置（提交 `e9985bc`）

**问题**：`generateStandardForLoop.go` 函数处理 `cond_br`（if/else）时，`then` 块中的 `return` 语句设置 `self.return_generated = true`，但进入 `else` 块前未重置该标志。导致 `else` 块中的 `emitIncAndPhi` 跳过 PHI 更新（`if (self_.return_generated) return;`），循环变量不递增，形成无限循环。

**修复**：在 `then` 块生成后、`else` 块生成前添加 `self_.return_generated = false;` 重置，与 `generateCondBrBlock` 中的模式一致。

**影响**：修复 2 个脚本（f081, f171）。

### 3.1 f070 输出差异深入调查（已完成调查，未修复）

**现象**：`AccountReadModel::project` 方法中 `foreach` + `if/elseif` + 复合赋值（`$balance += $e->data['amount']`）在 ReleaseSmall 下输出错误值。

**Debug 模式输出正确**：`balance=1100, tx_count=5`
**ReleaseSmall 输出错误**：`balance=-500, tx_count=2`（只处理了 withdrawn 事件）

**精确诊断**（通过逐迭代调试输出）：
- 第 1 次 deposited：`bal=1000`（正确：0+1000）
- 第 2 次 deposited：`bal=500`（错误：0+500，PHI 未回写上一轮的 1000）
- 第 3 次 withdrawn：`bal=-200`（错误：0-200，PHI 未回写）
- 第 4 次 deposited：`bal=-100`（使用第 3 次的 -200：-200+100）

**关键发现**：
1. deposited 分支（外层 if 的 THEN block）的 PHI 合并未生效
2. withdrawn 分支（ELSE 内嵌套 if 的 THEN block）的 PHI 合并生效了
3. 这**不是**优化器问题——`asm volatile` 内存屏障（循环头部、PHI 赋值后、循环回边 PHI 后）均无效
4. 这是 `generateCondBrBlock` 中 **THEN 分支的 PHI 生成路径**与嵌套 `generateCondBrBlock` 路径的差异导致的代码生成 bug

**尝试过的无效方案**：
- `std.mem.doNotOptimizeAway(reg_X)` — 对 struct 传值时只保护临时拷贝
- `asm volatile("" ::: .{ .memory = true })` 在 PHI 赋值后 — 无效
- `asm volatile("" ::: .{ .memory = true })` 在循环回边 PHI 后 — 无效
- `asm volatile("" ::: .{ .memory = true })` 在循环头部 — 无效

**最小化复现脚本**：`scripts/test_class_method.php`（已验证复现）

### 3.2 f090 输出差异调查（已完成调查，未修复）

## 五、已知问题

### 5.1 f070 — `generateCondBrBlock` THEN 分支 PHI 生成缺陷

**根因定位**：`generateCondBrBlock` 函数中，THEN 块的 PHI 合并赋值通过 `generateBrChain`（line ~13168）生成，而 ELSE 块内的嵌套 if/elseif 的 PHI 合并通过递归 `generateCondBrBlock`（line ~13118）生成。两条路径对 PHI 合并的处理方式可能不同，导致 THEN 分支的 PHI 值在跨迭代时丢失。

**复现条件**：
1. `foreach` 循环内
2. `if/elseif/else` 链
3. 代码在类方法内（有 `$this` 上下文）
4. 分支内有复合赋值（`$balance += ...`）

**不触发条件的对照测试**：
- 顶层代码（非类方法）→ 通过
- 纯数组访问（非对象属性）→ 通过
- 无 `$this->projections` 存储 → 通过

### 5.2 f090 — Promise.all 闭包变量捕获缺陷

**根因**：`Promise.all` 的回调聚合逻辑在 AOT 下返回 null，Debug 模式也错。可能是闭包 `use(&$var)` 引用传递在 AOT 下未正确实现。

### 5.3 `asm volatile` 性能开销

已回退所有 `asm volatile` 和 `doNotOptimizeAway` 改动，因为它们不解决 f070 问题且大幅增加编译时间（native_linker.zig 编译从 ~2 分钟增至 ~8 分钟）。
