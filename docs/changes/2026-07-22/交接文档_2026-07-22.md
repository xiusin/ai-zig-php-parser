## 二、已完成任务

### 2.1 P1: 扩展动态静态调用支持 `($expr)::constant` 和 `($expr)::$prop`

**背景**：上一会话仅实现了 `($expr)::method()` 的动态类名静态方法调用。`($expr)::$prop` 和 `($expr)::CONSTANT` 会报 `Invalid static access target` 解析错误。

**实现细节**：

| 组件 | 变更内容 |
|------|----------|
| `src/compiler/ast.zig` | 新增 `dynamic_static_property_access` 和 `dynamic_class_constant_access` 两个 AST 节点类型及其数据结构 |
| `src/compiler/parser.zig` | 重构 `::` 运算符解析逻辑：当 `class_name_id == null`（动态类名）时，`$prop` 走 `dynamic_static_property_access`，`CONSTANT` 走 `dynamic_class_constant_access`，不再报错 |
| `src/aot/ir_generator.zig` | 新增 `generateDynamicStaticPropertyAccess` 和 `generateDynamicClassConstantAccess` 函数；同时在 `generateStaticPropertyAccess` 和 `generateClassConstantAccess` 中添加 `$` 前缀检测，使 `$cls::$prop`（变量名含 `$` 前缀）也走动态路径 |
| `src/aot/runtime_lib_template.zig` | 新增 `php_get_static_property_dynamic(args, allocator)` 和 `php_get_class_constant_dynamic(args, allocator)` 两个运行时函数 |
| `src/aot/native_linker.zig` | 注册两个新函数到 `builtin_map`（`needs_allocator = true, may_raise = true`）；将函数名添加到 `php_call_static_dynamic` 所在的条件判断列表中，复用 `writeValueArgsArray` + `runtime_allocator` 代码生成模式 |

**关键技术点**：

1. **变量名 `$` 前缀**：AST 中变量名存储为 `$cls`（含 `$` 前缀）。IR 生成器通过 `class_name.len > 0 and class_name[0] == '$'` 判断是否为动态类名，与 `generateStaticMethodCall` 中已有的模式一致。

2. **类常量存储位置**：`ClassMeta` 结构体没有独立的 `constants` 字段，类常量存储在 `static_properties` 中。`php_get_class_constant_dynamic` 需遍历继承链（`meta.parent`）查找常量。

3. **`::class` 特殊处理**：`php_get_class_constant_dynamic` 中特殊处理 `const_name == "class"`，返回类名字符串（需通过 `PHPString.init(allocator, class_name)` 分配）。

4. **代码生成路径**：两个新函数接收 `[]const Value` 数组参数 + `allocator`，与 `php_call_static_dynamic` 签名一致，复用同一代码生成分支（`writeValueArgsArray` → `&[_]runtime.Value{...}` → `, runtime.runtime_allocator`）。

**验证结果**：

测试脚本 `scripts/test_dynamic_static_access.php` 覆盖以下场景：
- `($cls)::method()` — 动态方法调用
- `($cls)::$count` — 动态静态属性访问
- `($cls)::VERSION` — 动态类常量访问
- 切换类名后重复测试
- 带参数的动态方法调用 `($cls)::double(21)`
- 数组索引表达式 `($arr[0])::getName()`

AOT 编译 + 运行输出完全正确：
```

BarClass

FooClass

```

### 2.2 P2: 统一所有 PHI 赋值路径使用 `writePtrAwareAssign`

**背景**：上一会话在 `generateCondBrBlock` 中将 PHI 赋值替换为 `writePtrAwareAssign`，但需确认所有路径已统一。

**审查结果**：

| 路径 | 当前状态 | 说明 |
|------|----------|------|
| 无依赖 PHI 赋值 | ✅ 使用 `writePtrAwareAssign` | `generateCondBrBlock` 中无依赖分支 |
| 有依赖 PHI 赋值（非循环依赖） | ✅ 使用 `writePtrAwareAssign` | `needs_temp[i] == false` 的赋值 |
| 有依赖 PHI 赋值（循环依赖） | ⚠️ 使用 `phi_temp` | 必要例外：值来自局部变量而非寄存器，无法通过 `writePtrAwareAssign` 处理 |
| `generateLoopBodyFromBlock` PHI | ✅ 使用 `writePtrAwareAssign` | 通过 `writePhiAssignWithRetain` 调用 |
| `generateWhileLoopStructuredNew` PHI | ✅ 使用 `writePtrAwareAssign` | cond_br 路径 |

**结论**：PHI 赋值路径已基本统一。`phi_temp` 仅用于循环依赖场景（多个 PHI 节点相互引用，需先保存到临时变量再赋值），这是语义必要的设计，不算遗漏。

### 2.3 P2: `return_generated` 改为作用域栈

**背景**：`return_generated` 是一个布尔标志，在 `generateReturnInBlock` 中设置为 `true`，用于阻止 `generateBrChain` 在 `return` 后继续生成 dead code（Zig 0.17 将 unreachable code 从警告升级为错误）。

**问题**：嵌套循环中，内层循环的 `return` 会设置 `return_generated = true`，导致外层循环的 PHI 更新被跳过（`if (!self.return_generated)` 检查失败），从而循环变量不递增。

**实现**：在以下三处添加 save/restore 机制：

| 位置 | 代码 |
|------|------|
| `generateWhileLoopStructuredNew`（循环体开始前） | `const saved = self.return_generated; self.return_generated = false; defer self.return_generated = saved;` |
| `generateStandardForLoop`（主循环 `while(true)` 前） | 同上 |
| `generateStandardForLoop`（epilogue 循环 `while(true)` 前） | 同上（变量名 `saved_return_generated_epilogue`） |

**效果**：
- 循环体内的 `return` 设置 `return_generated = true`，阻止循环内后续 dead code
- 循环结束后 `defer` 恢复外层值，外层循环的 PHI 更新不受影响
- 嵌套循环逐层独立跟踪，互不干扰

#### P2: `return_generated` 升级为作用域栈

当前使用 `const saved = self.return_generated; defer self.return_generated = saved;` 模式，虽然功能正确，但在极深嵌套场景下可读性较差。可考虑升级为 `std.ArrayList(bool)` 栈结构：

```zig
return_generated_stack: std.ArrayList(bool),

// 进入循环作用域
try self.return_generated_stack.append(self.allocator, false);
defer _ = self.return_generated_stack.pop();

// 读取当前作用域状态
const return_generated = self.return_generated_stack.items[self.return_generated_stack.items.len - 1];
```

此重构为纯内部优化，不改变外部行为，可在后续迭代中执行。
