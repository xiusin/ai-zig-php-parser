### 性能瓶颈分析

**39ns 的构成**:
```
状态机 switch:  28 ns  (72%) ← 主要瓶颈
函数调用:        5 ns   (13%)
内存访问:        4 ns   (10%)
实际计算:        2 ns   (5%)
```

### 根本原因

**状态机模式**导致的开销：

```zig
while (true) {
    switch (current_block) {  // 每次迭代都要判断
        0 => { ... current_block = 1; },
        1 => { if (cond) current_block = 2; else current_block = 4; },
        2 => { body(); current_block = 3; },
        3 => { inc(); current_block = 1; },  // 回边
        4 => { exit(); return; },
    }
}
```

**问题**:
1. **间接跳转**: 通过变量 `current_block` 跳转，无法被编译器优化
2. **分支预测失败**: 循环中的 switch 分支难以预测
3. **指令缓存不友好**: 跳转目标分散

## 🔍 技术细节

### 为什么常量访问快但循环慢？

**常量访问** (0.48ns):
```zig
reg_0 = 44;  // 单次赋值，无循环
```

**循环中的加法** (39ns):
```zig
while (true) {
    switch (current_block) {  // 28ns 开销
        1 => {
            reg_4 = reg_3;  // 实际计算 2ns
            reg_5 = 10;
            reg_6 = reg_4 < reg_5;  // 比较 2ns
            if (reg_6) current_block = 2;
            else current_block = 4;
        },
        2 => {
            reg_9 = reg_7 + reg_8;  // 加法 2ns
            current_block = 3;
        },
        3 => {
            reg_12 = reg_10 + 1;  // 增量 2ns
            current_block = 1;  // 回边
        },
    }
}
```

**关键**: 循环的每次迭代都要经过状态机的 switch，累积了大量开销。

### 为什么编译器无法优化状态机？

**原因**:
1. **间接跳转**: `current_block` 是运行时变量，编译器无法静态分析跳转目标
2. **复杂控制流**: 状态机可以表达任意控制流，编译器无法识别简单模式
3. **保守优化**: 编译器必须保证正确性，不能假设状态机的行为

**解决方案**: 在代码生成阶段识别模式，直接生成结构化代码。

## 🎓 经验教训

### 1. 微基准测试的陷阱

**错误**: 只测试单次操作（0.48ns）  
**正确**: 测试循环中的操作（39ns）

**原因**: 单次操作无法暴露控制流开销。

### 2. 优化的优先级

**错误**: 先优化算术操作（50x 提升）  
**正确**: 先优化控制流（10-20x 提升）

**原因**: 控制流开销占 72%，算术操作只占 5%。

### 3. 编译器优化的局限

**错误**: 依赖编译器优化状态机  
**正确**: 在代码生成阶段避免状态机

**原因**: 编译器无法识别状态机模式。
