# AOT 编译器优化总结

## 当前状态（2026-02-10）

### ✅ 已完成的优化

#### 1. 控制流优化
- **结构化循环生成**：生成原生 `for`/`while` 循环
- **完全循环展开**：≤16 次迭代的循环完全展开
- **数学简化**：`for(i=0;i<N;i++) sum+=1` → `sum+=N`
- **死循环消除**：检测并移除不可达循环

#### 2. 数据流优化
- **Phi 节点支持**：正确处理三元运算符和分支合并
- **类型转换优化**：自动插入 i64/f64/Value 转换
- **Alloca 优化**：消除不必要的指针解引用
- **死代码消除**：移除未使用的指令

#### 3. 内存优化
- **寄存器分配**：优化的寄存器使用
- **栈变量优化**：减少栈分配
- **常量折叠**：编译时计算常量表达式

### 🔍 瓶颈分析

#### 1. 字符串操作（最大瓶颈）
**问题**：
- 每次 `php_concat` 都调用 `php_value_to_string` + GC + 内存分配
- 常量字符串在循环内重复计算
- 没有字符串池化

**解决方案**：
- [ ] 实现循环不变量提升（LICM）
- [ ] 优化 runtime `php_concat` 实现
- [ ] 添加字符串池化
- [ ] 内联小字符串操作

**预期提升**：100-1000x

#### 2. 数组操作
**问题**：
- 每个元素 `push` 都是动态分配
- 常量数组在运行时构建
- 数组访问有边界检查开销

**解决方案**：
- [ ] 编译时生成常量数组
- [ ] 优化数组访问（消除已知安全的边界检查）
- [ ] 内联小数组操作

**预期提升**：5-10x

#### 3. Runtime 调用开销
**问题**：
- 所有操作都通过 runtime 函数
- 没有内联优化
- 类型转换开销

**解决方案**：
- [ ] 内联常用 runtime 函数
- [ ] 特化类型操作（i64 直接运算，不转 Value）
- [ ] 减少不必要的类型转换

**预期提升**：2-5x

### 🎯 下一步优化优先级

#### P0（关键）
1. **循环不变量提升（LICM）**
   - 检测循环内的常量表达式
   - 提升到循环外
   - 预期：字符串性能提升 100x

2. **Runtime 函数内联**
   - 内联 `php_concat`、`php_add` 等
   - 减少函数调用开销
   - 预期：整体性能提升 2x

#### P1（重要）
3. **常量数组优化**
   - 编译时生成数组字面量
   - 预期：数组性能提升 5x

4. **字符串池化**
   - 复用相同字符串
   - 减少内存分配
   - 预期：字符串性能提升 2x

#### P2（增强）
5. **边界检查消除**
   - 分析数组访问安全性
   - 消除已知安全的检查
   - 预期：数组性能提升 1.5x

6. **类型特化**
   - 为 i64/f64 生成专用代码
   - 避免 Value 包装
   - 预期：算术性能提升 2x

---

**结论**：AOT 编译器的**编译时优化已经很好**（循环展开、数学简化、死代码消除等）。性能差距主要来自 **runtime 实现**，不是编译器本身。下一步应该优化 runtime 函数，而不是继续添加编译器优化。
