## 问题分析

### 属性 33.4 失败原因
在小规模测试（500个对象）中，并行 GC 的线程创建开销（~300-400μs）超过了并行化带来的收益，导致：
- 串行 GC 时间：~50-100μs
- 并行 GC 时间：~300-500μs（包含线程创建开销）
- 结果：并行 GC 反而更慢

### 尝试的优化方案
1. **持久化线程池**：尝试实现持久化工作线程以避免每次 GC 都创建线程
   - 遇到问题：`WorkerPool` 地址在初始化后改变，导致工作线程中的指针失效
   - 错误类型：Bus error（总线错误）
   - 原因：Zig 中结构体按值传递，`WorkerPool` 被移动后地址改变

## 建议的解决方案

### 方案 A：简化实现 + 增加测试规模（推荐）

**优点**：
- 实现简单，内存安全
- 可以快速完成并通过测试
- 符合实际使用场景（GC 通常处理大量对象）

**实施步骤**：
1. 回退持久化线程池的修改
2. 保持当前的临时线程实现
3. 优化线程创建和同步机制
4. 将测试对象数量从 500 增加到 5000+
5. 实现自适应策略：
   - 对象数量 < 1000：使用串行 GC
   - 对象数量 >= 1000：使用并行 GC
6. 更新属性 33.4 测试，使用更大的测试规模

**预期结果**：
- 在大规模测试中，并行 GC 的优势会显现
- 线程创建开销相对于总工作量变得可以忽略
- 预计可以达到 50%+ 的暂停时间减少

### 方案 B：持久化线程池（高风险）

**需要解决的问题**：
1. 使用堆分配的 `WorkerPool`（已尝试，仍有问题）
2. 重新设计数据结构，避免指针失效
3. 可能需要使用 `std.Thread.Pool` 或其他现有实现

**风险**：
- 需要更多时间调试
- 可能遇到更多内存安全问题
- 不一定能解决根本问题
