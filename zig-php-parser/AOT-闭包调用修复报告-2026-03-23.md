# AOT 闭包调用修复报告

**日期**: 2026-03-23  
**修复问题**: test_209_memoize.php - 嵌套闭包调用 InvalidCallback 错误  
**影响范围**: AOT 编译器代码生成逻辑

---

## 问题描述

test_209_memoize.php 在 AOT 模式下运行时抛出 `InvalidCallback` 错误。测试用例涉及：
- `memoize()` 函数接收一个闭包作为参数
- 返回一个新闭包，该闭包内部调用传入的闭包
- 嵌套闭包调用场景

### 错误现象

```
error: InvalidCallback
runtime_lib.zig:3927:5: in php_invoke_callable
```

调用栈显示：`__main__` → `memoize($fib)` → `__closure_1` → `php_invoke_callable($fn)` 失败

---

## 根本原因分析

### 问题定位

通过调试发现，在 `memoize()` 函数中，捕获的 `$fn` 参数在闭包创建时变成了 `null`。

### 代码生成 Bug

在生成的 `__main__` 函数中，`$fib` 变量的赋值逻辑有问题：

```zig
// 创建 $fib 闭包
reg_5 = try runtime.php_create_closure(...);

// 存储到全局变量
try setGlobalVar("$fib", reg_5);

// BUG: global_set 指令错误地释放并清空了寄存器
reg_5.release(runtime.runtime_allocator);
reg_5 = runtime.Value.initNull();

// 后续的 store 指令使用已经变成 null 的寄存器
runtime.ref_aware_store(reg_0, reg_5);  // 将 null 赋值给 $fib!
```

### Bug 来源

在 `src/aot/native_linker.zig` 的 `global_set` 指令处理中（第9240-9256行）：

```zig
.global_set => |op| {
    if (op.value) |val| {
        if (is_alloca) {
            try writer.print("    try setGlobalVar(\"{s}\", reg_{d}.*);\n", ...);
        } else {
            try writer.print("    try setGlobalVar(\"{s}\", reg_{d});\n", ...);
            // BUG: 立即释放寄存器
            try writer.print("    reg_{d}.release(runtime.runtime_allocator);\n", ...);
            try writer.print("    reg_{d} = runtime.Value.initNull();\n", ...);
        }
    }
},
```

**问题**：
1. `setGlobalVar()` 会 `retain()` 值，全局变量表持有一个引用
2. 代码生成器立即 `release()` 并清空寄存器
3. 但后续的 `store` 指令仍然使用这个寄存器
4. 导致局部变量被赋值为 `null`

---

## 修复方案

### 修复逻辑

移除 `global_set` 指令中对寄存器的释放和清空操作，让寄存器的正常生命周期管理来处理引用计数。

### 修复代码

```zig
// src/aot/native_linker.zig (第9240-9256行)
.global_set => |op| {
    if (op.value) |val| {
        const escaped_name = try self.escapeString(op.name);
        defer self.allocator.free(escaped_name);
        const is_alloca = if (self.current_alloca_regs) |regs| regs.contains(val.id) else false;
        if (is_alloca) {
            try writer.print("    try setGlobalVar(\"{s}\", reg_{d}.*);\n", .{ escaped_name, val.id });
        } else {
            try writer.print("    try setGlobalVar(\"{s}\", reg_{d});\n", .{ escaped_name, val.id });
            // setGlobalVar 会 retain 值，全局变量表持有一个引用
            // 寄存器继续持有原引用，由后续的正常清理逻辑处理
            // 不在这里释放寄存器，避免影响后续使用该寄存器的指令
        }
    }
},
```

### 修复原理

1. **引用计数正确性**：
   - `setGlobalVar()` retain 值 → 全局变量表持有引用
   - 寄存器保持原引用 → 后续指令可以继续使用
   - 函数结束时的 cleanup 代码会释放寄存器

2. **避免过早释放**：
   - 不在 `global_set` 中释放寄存器
   - 让 IR 的正常生命周期分析来决定何时释放
   - 保证后续指令能正确访问寄存器的值

## 技术要点

### 引用计数管理原则

1. **所有权清晰**：
   - 全局变量表持有一个引用
   - 寄存器持有一个引用
   - 每个引用都有明确的释放时机

2. **生命周期分离**：
   - 全局变量的生命周期由全局变量表管理
   - 寄存器的生命周期由函数作用域管理
   - 不要在一个操作中混淆两者

3. **避免过早优化**：
   - 不要在指令处理中做过多的引用计数操作
   - 让编译器的正常分析来决定何时释放
   - 保持代码生成的简单性和正确性

### 代码生成最佳实践

1. **指令语义单一**：
   - 每个 IR 指令只做一件事
   - `global_set` 只负责设置全局变量
   - 不要附加额外的副作用

2. **寄存器不可变性**：
   - 指令不应该修改输入寄存器的值
   - 保持寄存器在指令执行前后的一致性
   - 让后续指令能够正确访问寄存器

3. **清理逻辑统一**：
   - 所有寄存器的释放由统一的 cleanup 代码处理
   - 不要在各个指令中分散释放逻辑
   - 保持代码生成的可维护性
