# 修复 AOT 编译器与类型系统问题计划

针对您反馈的 `native_linker.zig` 编译错误和 Zig 代码类型不匹配问题，我制定了以下修复计划。

## 1. 核心问题分析

1.  **编译错误 (`no field named 'ir'`)**: `NativeLinker` 结构体中不存在 `ir` 字段，但在生成 `load`/`store` 指令时尝试调用 `self.ir.getRegister`。这是因为代码试图获取寄存器信息，但使用了错误的路径。
2.  **类型不匹配 (`expected *Value, found **Value`)**: 生成的 Zig 代码中，对于 `store` 和 `load` 操作，`ptr_prefix`（是否加 `&`）的判断逻辑有误。
    *   目前代码试图通过 `ptr_reg.is_ref` 判断，但因无法获取 `ptr_reg` 而失败。
    *   在生成的 Zig 代码中，`alloca` 指令产生的寄存器被声明为指针 (`*runtime.Value`)，而普通寄存器被声明为值 (`runtime.Value`)。
    *   如果不加区分地对所有寄存器加 `&`，会导致对已经是指针的 `alloca` 寄存器再次取地址，造成类型错误。

## 2. 实施步骤

### 步骤 1: 修复 `NativeLinker` 上下文管理
在 `generateFunction` 中，我们需要将 `alloca_registers` 的信息传递给 `NativeLinker` 实例，以便在生成指令时可以查询哪些寄存器是指针。

*   **文件**: `src/aot/native_linker.zig`
*   **操作**: 在 `generateFunction` 方法中，将 `alloca_registers` 赋值给 `self.current_alloca_regs`。

```zig
// 在 generateFunction 中
self.current_alloca_regs = &alloca_registers;
defer self.current_alloca_regs = null;
```

### 步骤 2: 修正指令生成逻辑
修改 `generateInstructionSimple` 和 `generateInstructionDirect` 函数，移除错误的 `self.ir` 调用，改用 `current_alloca_regs` 判断地址前缀。

*   **文件**: `src/aot/native_linker.zig`
*   **操作**:
    1.  移除 `const ptr_reg = self.ir.getRegister(op.ptr.id);`
    2.  修改 `ptr_prefix` 的计算逻辑：
        ```zig
        // 检查是否是 alloca 寄存器（即指针类型）
        const is_ptr = if (self.current_alloca_regs) |regs| regs.contains(op.ptr.id) else false;
        // 如果是指针，不需要取地址；如果是值，需要取地址
        const ptr_prefix = if (is_ptr) "" else "&";
        ```
    3.  应用此修改到 `store` 和 `load` 指令的所有相关分支。

### 步骤 3: 验证修复
完成修改后，我们将能够重新编译项目。建议您运行 `test/aot_diff/concurrency_basic.php` 来验证生成的代码是否正确。

## 3. 关于 Channel 挂起
关于您提到的 Channel 挂起机制（从线程阻塞改为协程挂起），这是一个涉及运行时核心逻辑的改进。为了保证任务的聚焦和稳定性，我建议**在完成上述 AOT 修复并验证通过后**，再单独进行 Channel 的改造。届时我们需要修改 `src/runtime/channel.zig` 并对接 `Scheduler` 的 `suspend`/`resume` API。

## 6. 当前已知语义缺口与风险（重要）

### 6.1 LSB 语义的“真实 PHP”差异：self/parent/static 的绑定来源不同（P0）

当前实现为了先推进差异收敛，采用了相对简化的模型：在 AOT runtime 用 `current_called_class` 同时解析 `self/static/parent`。

但真实 PHP 中：

- `self::` 是**早绑定**：绑定到“方法定义所在类（lexical scope class）”
- `parent::` 也是早绑定：绑定到“方法定义所在类的 parent”
- `static::` 才是**后期静态绑定（LSB）**：绑定到“调用点的 called class（get_called_class）”

因此在如下场景会出错（真实 PHP 的关键点）：

- `Child::foo()` 里执行 `parent::bar()`，而 `bar()` 内部使用 `static::baz()`
  - 正确：`static::` 仍应解析为 `Child`
  - 简化实现可能会变成 `Parent`（取决于 current_called_class 的更新策略）

结论：当前实现主要保证了 `static::`/`new static` 的“可用性”和 AOT/解释器收敛，但**尚未严格满足 PHP 的 self/parent/static 分离语义**。这需要下一阶段引入“scope class + called class”双上下文模型。

### 6.2 并发安全风险：current_called_class 为全局变量（P0）

AOT runtime 当前的 `current_called_class` 是全局变量。在存在并发（go routines / 多线程执行）时，可能出现数据竞争与跨协程污染，导致 `static::` 在高并发下出现非确定性行为。

建议方向：

- 将 `current_called_class` 改为 threadlocal（至少线程隔离）
- 更进一步：绑定到 scheduler 的协程上下文（goroutine-local），使用栈式 push/pop（保证可重入与嵌套调用正确）

### 6.3 “返回类型 static”目前仅解析/传播，未做运行时校验（P1）

目前 `: static` 能被解析成类型名，并参与 IR 类型表达（在 AOT 侧通常会降级成动态 `php_value` 或 `php_object<static>` 形式），但真实 PHP 的语义是：若声明 `function f(): static`，返回值必须是“called class 的实例”，否则抛 TypeError。

当前尚未做：

- 解释器：return 路径对 `Method.return_type` 执行 static/self 类型校验
- AOT：在函数 return 前插入必要的 runtime check（或统一由 runtime wrapper 完成）

## 7. 后续开发任务清单（建议优先级 + 技术落点）

### P0（必须尽快做，影响语义正确性/并发安全）

1. **LSB 双上下文模型：scope class 与 called class 分离**
   - 目标：严格实现 `self/parent` 早绑定 + `static` 后绑定
   - 解释器侧建议：
     - 增加 `VM.called_class`（或 `VM.current_called_class`）
     - 方法执行时同时维护：
       - `current_class` = scope class（方法定义所在类）
       - `called_class` = 调用点类（对象真实类或静态调用类）
   - AOT 侧建议：
     - `ClassMethod` 增加 `declaring_class` 指针（导入 trait/继承时也要正确设置）
     - 调用 method.func 前设置 `current_scope_class`，并把 `current_called_class` 保持为调用点类
     - `resolveSpecialClassName`：
       - self/parent 读 `current_scope_class`
       - static 读 `current_called_class`
2. **并发隔离：把 called/scope 上下文做 goroutine-local**
   - threadlocal 只能解决线程竞争；若一个线程上多协程交错执行，仍可能污染
   - 最佳落点通常是 Scheduler 上下文（每协程一个小结构体：`called_class_stack`, `scope_class_stack`）
3. **补齐 get_called_class / forward_static_call(_array)**
   - 这些是 LSB 生态里高频 API，用来把 called class 显式暴露给用户态代码
   - 解释器与 AOT 都应提供同名 builtin，并共用同一套 called-class 解析来源

### P1（中期完善：类型系统与更多语义边界）

1. **返回类型 static/self/parent 的运行时校验**
   - 解释器：
     - 在 return 触发时，根据 `Method.return_type` 做检查
     - `static` 校验基于 called class；`self/parent` 基于 scope class
   - AOT：
     - 优先实现“运行时 wrapper 校验”：方法返回时由 runtime 统一检查（便于保持 lowering 简单）
2. **静态属性/类常量的 LSB 语义补齐**
   - `self::$p`（早绑定） vs `static::$p`（后绑定）
   - `self::CONST` vs `static::CONST`
3. **解释器 Bytecode 生成链路补齐（如果仍计划保留字节码模式）**
   - 当前 VM 已能 eval `static_method_call/static_property_access/class_constant_access`，但字节码生成端未完全覆盖这些 AST tag 时，会出现“解析得到 AST，但编译不出 opcode”的断层。

### P2（长期优化：性能与可维护性）

1. **把“可释放字符串/静态字符串”从约定变成类型约束**
   - 方向：区分 `OwnedString`/`StaticString` 或在 `PHPString` 构造层强制标记并防误用
2. **把 OOP 元数据的“declaring class / overriding chain”显式建模**
   - 有助于正确实现 `ReflectionMethod::getDeclaringClass()` 等反射语义
3. **增量式引入“PHP 作为 oracle”的对齐测试**
   - 建议先挑 20-50 个高价值用例（LSB、magic methods、serialization、traits、visibility、exception）
   - 形成稳定回归集后，再扩大覆盖面
