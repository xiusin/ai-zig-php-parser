# 高效内存管理方案

## 🎯 方案对比

### 方案A: ArrayList
- **时间复杂度**: O(n) 查找
- **空间复杂度**: O(n)
- **优点**: 简单、安全
- **缺点**: 变量多时慢（n>100时明显）

### 方案B: 预分配HashMap (推荐)
- **时间复杂度**: O(1) 查找
- **空间复杂度**: O(n)
- **优点**: 高效、保持原有性能
- **缺点**: 需要准确估算容量

### 方案C: 两级HashMap
- **时间复杂度**: O(1) 查找
- **空间复杂度**: O(n)
- **优点**: 隔离作用域，避免冲突
- **缺点**: 复杂度高

## 💡 推荐：方案B - 预分配HashMap

### 核心思路
1. 在函数开始时，预分配HashMap容量
2. 在foreach开始时，额外预分配容量
3. 避免HashMap grow导致的unreachable

### 实现

```zig
// 在generateFunction开始时
pub fn generateFunction(...) !void {
    // 预分配足够的容量（估算：参数 + 局部变量 + 临时变量）
    const estimated_vars = 50; // 保守估计
    try self.var_registers.ensureTotalCapacity(self.allocator, estimated_vars);
    try self.var_usage.ensureTotalCapacity(self.allocator, estimated_vars);
    try self.ref_vars.ensureTotalCapacity(self.allocator, estimated_vars);
    
    // ... 原有代码
}

// 在generateForeachStmt开始时
fn generateForeachStmt(...) !void {
    // foreach可能引入新变量，额外预分配
    const current_capacity = self.var_registers.capacity();
    const needed_capacity = current_capacity + 20; // foreach变量 + try-catch变量
    try self.var_registers.ensureTotalCapacity(self.allocator, needed_capacity);
    try self.var_usage.ensureTotalCapacity(self.allocator, needed_capacity);
    
    // ... 原有代码
}
```

### 优点
1. **保持O(1)性能** - HashMap查找仍然是O(1)
2. **避免grow** - 预分配足够容量，不会触发grow
3. **简单** - 只需添加几行代码
4. **向前兼容** - 不改变API

### 容量估算策略

**保守策略**（推荐）:
- 函数级别: 50个变量
- foreach级别: +20个变量
- 嵌套foreach: 每层+20个变量

**动态策略**（可选）:
```zig
// 根据AST分析估算变量数量
fn estimateVarCount(node: *const Node) usize {
    var count: usize = 0;
    // 遍历AST，统计变量声明
    return count;
}
```

## 📊 性能对比

### ArrayList方案
- 查找: O(n) - 平均20次比较
- 插入: O(n) - 平均10次比较
- 删除: O(n) - 平均10次比较
- **总体**: 慢3-5倍

### 预分配HashMap方案
- 查找: O(1) - 1次哈希
- 插入: O(1) - 1次哈希
- 删除: O(1) - 1次哈希
- **总体**: 保持原有性能

## ⚠️ 风险评估

### 低风险
- 只是预分配容量，不改变逻辑
- 如果容量不够，HashMap会自动grow（虽然可能unreachable）
- 可以逐步调整容量大小

### 缓解措施
- 从保守的容量开始（50）
- 监控实际使用情况
- 根据需要调整
