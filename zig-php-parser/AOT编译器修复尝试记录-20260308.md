### 方案1: 替换HashMap为ArrayList ❌

**思路**: 用ArrayList替代StringHashMap，避免HashMap的grow问题。

**实现**:
```zig
const VarRegister = struct {
    name: []const u8,
    reg: IR.Register,
};

var_registers: std.ArrayListUnmanaged(VarRegister),

fn getVarRegister(self: *const Self, name: []const u8) ?Register {
    for (self.var_registers.items) |vr| {
        if (std.mem.eql(u8, vr.name, name)) return vr.reg;
    }
    return null;
}
```

**结果**: ❌ 失败
- var_registers修复成功
- 但var_usage、ref_vars等所有HashMap都有同样的问题
- 需要替换所有HashMap，工作量太大

    // 预分配HashMap容量
    const estimated_capacity = self.var_registers.count() + 10;
    try self.var_registers.ensureTotalCapacity(self.allocator, estimated_capacity);
    try self.var_usage.ensureTotalCapacity(self.allocator, estimated_capacity);

**结果**: ❌ 失败

## 🔍 关键发现

### 1. 问题的根本原因
- **不是简单的HashMap bug**
- **可能是Zig 0.15.2的标准库问题**
- **或者是我们的内存管理有深层问题**

### 2. 所有修复都让情况变差或不变
- 修复var_registers → var_usage也有问题
- 预分配容量 → 引入Double free
- 修改deinit → 更多错误

### 3. Double free的出现
ensureTotalCapacity虽然避免了unreachable，但引入了Double free：
```
error(gpa): Double free detected. Allocation: 
 First free: 
 Second free: 
```

这说明预分配容量后，HashMap的内部状态管理出现了问题。

## 💡 结论

### 问题的复杂性
1. **不是单一的HashMap问题** - 所有HashMap都受影响
2. **不是简单的容量问题** - 预分配也会引入新问题
3. **可能是Zig标准库bug** - 或者是我们的使用方式有问题
