### 问题的本质

经过多次尝试，问题的本质是：

1. **HashMap内部状态损坏** - 某个地方破坏了HashMap的内部指针
2. **内存地址无效** - 传给free的地址不是有效的分配地址
3. **Allocator状态不一致** - 可能使用了不同的allocator

**关键发现**: 
- 问题不在deinit本身
- 问题不在put操作本身
- 问题在HashMap grow时的free操作
- 说明HashMap内部存储的地址是无效的

### 可能的根本原因

1. **HashMap的metadata或entries指针被破坏**
   - 某个地方错误地修改了HashMap的内部字段
   - 导致free时使用了无效地址

2. **空HashMap `.{}` 的共享状态**
   - 多个空HashMap可能共享某些内部状态
   - 修改一个会影响其他

3. **Allocator的vtable被破坏**
   - 某个地方错误地修改了allocator的vtable
   - 导致free调用了错误的函数

## 💡 建议的解决方案

### 方案1: 深入调试 (推荐)

使用内存调试工具找出具体的内存问题：

```bash
# 使用Valgrind
valgrind --leak-check=full --track-origins=yes \
  ./zig-out/bin/php-interpreter --compile test_0003.php

# 或使用AddressSanitizer
zig build -Doptimize=Debug -Dsanitize=address
./zig-out/bin/php-interpreter --compile test_0003.php
```

### 方案2: 使用不同的数据结构

替换StringHashMapUnmanaged为其他数据结构：

```zig
// 使用ArrayList + 线性查找（简单但慢）
var_registers: std.ArrayListUnmanaged(struct {
    name: []const u8,
    reg: Register,
})

// 或使用BTreeMap（更稳定）
var_registers: std.BTreeMapUnmanaged([]const u8, Register)
```

### 方案3: 完全重写HashMap管理

创建自定义的HashMap包装器，确保内存安全：

```zig
const SafeHashMap = struct {
    inner: std.StringHashMapUnmanaged(Register),
    allocator: Allocator,
    is_valid: bool = true,
    
    pub fn deinit(self: *Self) void {
        if (!self.is_valid) return;
        self.inner.deinit(self.allocator);
        self.is_valid = false;
    }
};
```

### 方案4: 临时workaround

跳过有函数定义的测试，专注于其他功能：

```zig
// 在generateFunctionDecl开始处
if (std.mem.eql(u8, func_name, "func_3")) {
    // 跳过特定函数
    return;
}
```
