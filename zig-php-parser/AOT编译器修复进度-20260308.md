## ⚠️ 当前问题

### unreachable panic in Allocator (42%失败)

**错误堆栈**:
```
thread XXXXX panic: reached unreachable code
/opt/homebrew/Cellar/zig/0.15.2/lib/zig/std/mem/Allocator.zig:147:25: in grow
/opt/homebrew/Cellar/zig/0.15.2/lib/zig/std/hash_map.zig:1296:30: in put
```

**触发条件**:
- HashMap在put时需要grow
- grow时需要释放旧内存
- 旧内存地址无效，触发unreachable

**影响范围**:
- 所有包含函数定义的脚本
- 约42%的测试用例

### 根本原因分析

经过多次尝试，问题可能是：

1. **HashMap内部状态损坏** - 某个地方破坏了HashMap的内部指针
2. **Allocator状态不一致** - 使用了不同的allocator分配和释放
3. **内存被提前释放** - HashMap的key或value指向了已释放的内存

### 尝试过的方案

| 方案 | 结果 | 说明 |
|------|------|------|
| 只在非空时deinit | ❌ 失败 | 还是触发unreachable |
| 使用putAssumeCapacity | ❌ 失败 | 问题不在put本身 |
| 添加ensureTotalCapacity | ❌ 失败 | 问题在grow的free操作 |
| 添加clearRetainingCapacity | ❌ 失败 | 还是触发unreachable |
| 不deinit临时HashMap | ⚠️ 内存泄漏 | 会导致内存泄漏 |

## 💡 可能的解决方案

### 方案A: 使用ArenaAllocator (推荐)
为每个函数创建独立的Arena，函数结束时统一释放：

```zig
pub fn generateFunctionDecl(self: *Self, node: *const Node) !void {
    var arena = std.heap.ArenaAllocator.init(self.allocator);
    defer arena.deinit();
    const func_allocator = arena.allocator();
    
    // 使用func_allocator进行所有临时分配
    // 函数结束时自动释放所有内存
}
```

**优点**:
- 避免手动管理HashMap生命周期
- 自动释放所有临时内存
- 性能更好（批量释放）

**缺点**:
- 需要修改很多地方
- 需要区分临时和持久分配

### 方案B: 使用FixedBufferAllocator
为HashMap预分配固定大小的缓冲区：

```zig
var buffer: [1024 * 1024]u8 = undefined;
var fba = std.heap.FixedBufferAllocator.init(&buffer);
self.var_registers = std.StringHashMapUnmanaged(Register){};
// 使用fba.allocator()进行HashMap操作
```

**优点**:
- 避免动态分配
- 不会触发grow

**缺点**:
- 需要预估大小
- 可能溢出

## 📝 技术笔记

### HashMap的内部结构
```zig
pub const StringHashMapUnmanaged = struct {
    metadata: ?[*]Metadata,  // 元数据数组
    entries: ?[*]Entry,       // 条目数组
    size: usize,              // 当前大小
    available: usize,         // 可用空间
};
```

当HashMap grow时：
1. 分配新的metadata和entries
2. 复制旧数据到新位置
3. **释放旧的metadata和entries** ← 这里触发unreachable

### 可能的bug位置
- `hash_map.zig:1296` - grow函数中的free调用
- `Allocator.zig:147` - free函数中的unreachable
