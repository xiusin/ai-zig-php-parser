## 最终修复方案

### 核心策略

采用**三层防护**策略，确保内存安全：

1. **寄存器初始化为null** - 避免未定义行为
2. **store指令自动释放旧值** - 解决变量重新赋值的泄漏
3. **函数结束时释放所有临时值** - 确保无遗漏

### 实施细节

#### 修改1：寄存器初始化 ✅

**文件**: `src/aot/native_linker.zig` (第240-250行)

```zig

// 修改后
var reg_{d}: runtime.Value = runtime.Value.initNull();
```

**效果**: 所有寄存器都有明确的初始值，可以安全调用`release()`

#### 修改2：store指令释放旧值 ✅

**文件**: `src/aot/native_linker.zig` (第1227-1232行)

```zig
// 修改前
{s} = {s};

// 修改后
{s}.release(runtime.runtime_allocator);  // 释放旧值
{s} = {s};                                // 赋值新值
```

**效果**: 变量重新赋值时，旧值被自动释放，解决了循环中的主要泄漏

#### 修改3：移除循环cleanup ✅

**文件**: `src/aot/native_linker.zig` (第560-590行, 720-770行)

**原因**: 循环cleanup会导致双重释放，因为：
1. 临时值在store指令中已经被释放
2. 再次释放会导致段错误

**效果**: 避免双重释放，程序稳定运行

### 问题：大规模循环段错误

**现象**:
```

runtime_lib.zig:88:17: in release
```

**可能原因**:

1. **双重释放**
   - 某个值被释放了两次
   - 第二次释放时访问已释放的内存

2. **引用计数错误**
   - PHPString的ref_count管理有bug
   - 可能在某处ref_count被错误地减少

3. **内存对齐问题**

   - 地址`0x1007a00a0`可能是损坏的指针

   - 让函数结束时的cleanup处理
   - 简单但有效

### 遇到的陷阱

1. **双重释放**
   - 循环cleanup + store释放 = 双重释放
   - 解决：移除循环cleanup

2. **未初始化变量**
   - undefined + release() = 未定义行为
   - 解决：初始化为null

3. **过度释放**
   - 释放变量值 = 段错误
   - 解决：只在store时释放旧值
